# 아이디어 정리

구현 전에 무엇을 해결할지 결정한다. 이 단계만 요청받았다면 제품 코드는 수정하지 않는다.

1. 대화에서 목적과 맥락을 먼저 찾는다. 프로젝트가 있으면 `AGENTS.md`, 유사 기능, 관련 문서를 좁게 읽는다. 새 프로젝트는 생성 전에도 탐색할 수 있다.
2. 영향을 받는 사용자, 현재 문제, 원하는 성공 장면, 범위 밖의 일, 제약을 정리한다. 답을 이미 받은 질문은 반복하지 않는다.
3. 결정을 바꾸는 미확정 사항만 질문한다. 선택지가 도움이 되면 추천안을 포함한 짧은 선택지를 준다. 질문 도구가 없으면 일반 대화로 묻는다. 답을 기다리는 동안 독립적인 조사는 진행한다.
4. 실질적인 선택이 있다면 2~3개 대안을 비교한다. 기존 구현 활용 가능성, 비용, 실패 시 복구, 유지보수 부담을 근거로 추천한다. 선택지가 사실상 하나면 억지로 대안을 만들지 않는다.
5. 정상 흐름과 중요한 실패·취소·재시도·권한·빈 데이터 흐름을 확인한다. CLI나 백엔드는 사용자 화면 대신 호출자와 시스템 상태를 기준으로 생각한다.
6. [양식](references/brainstorm-template.md)에 결정, 이유, 미확정 사항과 완료 기준을 남긴다. 기본 경로는 `docs/workflow/<주제>/brainstorm.md`다. 기존 문서 관례가 있으면 따른다.

문서를 만든 뒤 핵심 결정과 남은 질문을 전달한다. 계획까지 요청받았으면 이어서 계획을 작성한다. 아이디어 정리만 요청받았으면 문서에서 마친다.
