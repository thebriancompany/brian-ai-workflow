# 구현 계획

다른 채팅에서도 바로 구현할 수 있도록 범위, 변경 지점, 순서, 완료 증거를 남긴다.

## 맥락 확인

- 입력한 요구사항과 관련 아이디어 문서를 읽는다. 문서는 주제와 현재 코드의 일치 여부로 선택한다. 요구사항이 충분하면 아이디어 단계를 생략한다.
- `AGENTS.md`, 변경 대상과 호출부, 의존성 버전, 기존 테스트, 실행 스크립트와 CI를 확인한다. 문서에 나온 경로와 API가 현재도 존재하는지 대조한다.
- 여러 앱이 있는 저장소는 변경하는 패키지와 공유 계약, 각 명령을 실행할 폴더를 구분한다.
- 버전별 API, 신규 의존성 또는 외부 서비스 동작이 불확실하면 해당 버전의 공식 문서로 확인한다. 조사한 내용과 추론을 구분하고 출처를 남긴다.

## 계획 작성

1. 목표, 범위 밖의 일, 전제와 중요한 결정을 적는다. 기존 아키텍처를 따르며 구현과 무관한 개선을 추가하지 않는다.
2. 사용자나 호출자의 정상·실패 흐름을 따라 누락을 찾는다. 권한, 데이터 일관성, 동시성, 취소, 호환성은 관련 있는 경우에만 다룬다.
3. 완료 기준마다 관찰 가능한 결과와 검증 방법을 짝지어 적는다. 테스트의 종료 코드가 0이어도 해당 요구사항을 검증하지 않으면 증거가 아니다.
4. 실행할 작업 폴더와 저장소에서 확인한 명령을 적는다. 아직 존재하지 않는 테스트는 만들 파일과 확인할 동작을 구분한다. 수동 검증은 순서와 기대 결과를 쓴다.
5. 변경 파일, 의존 순서, 위험에 맞는 테스트를 작업으로 분해한다. 큰 변경은 각 단계가 동작하고 검증 가능한 단위가 되도록 나눈다. 파일 수나 줄 수만으로 강제 분할하지 않는다.
6. 마이그레이션이나 공개 계약 변경이 있으면 호환 기간, 적용 순서, 되돌리기 방법을 포함한다.

기본 경로는 `docs/workflow/<주제>/plan.md`다. [계획 양식](references/plan-template.md)을 작업 크기에 맞춰 줄이거나 확장한다. 작은 수정은 목표·작업·검증만으로 충분하다.

## 자체 검토와 완료

저장 전에 경로와 명령의 타당성, 모호한 완료 기준, 누락된 의존성, 불필요한 추상화, 안전하게 나눌 수 있는 경계를 점검한다. 계획을 좋아 보이게 만들기 위해 사용자의 요구나 검증 수준을 낮추지 않는다. 요구를 바꾸는 결정만 사용자에게 확인한다.

계획만 요청받았으면 문서와 중요한 결정으로 마친다. 구현까지 요청받았으면 계획을 기준으로 이어서 수행한다. 자동으로 이슈를 만들거나 브랜치를 게시하지 않는다.
