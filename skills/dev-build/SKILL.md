# 구현과 검증

## 1. 입력과 현재 상태

- 계획 경로가 있으면 읽고 요청 범위, 완료 기준, 단계, 관련 파일을 추출한다. 계획이 없어도 작은 수정이나 명확한 요구사항은 간단한 작업 목록으로 바로 구현한다.
- 관련 계획이 여러 개면 대화와 주제로 식별한다. 식별할 수 없을 때만 묻는다. 계획에 `done`이 있어도 현재 코드와 완료 증거를 대조한다.
- 적용되는 `AGENTS.md`, 변경 대상·호출부, 의존성 파일, 기존 테스트, 스크립트와 CI를 확인한다. 현재 작업 트리의 사용자 변경을 구분해 보존한다.
- 적합한 현재 체크아웃이나 작업 브랜치를 재사용한다. 새 브랜치가 필요하면 프로젝트 규칙을 따르고, 별도 규칙이 없으면 `feature/<주제>`를 쓴다. 새 워크트리나 브랜치를 모든 수정에 강제하지 않는다.
- 사용자가 구현을 요청했다면 다시 시작 승인을 묻지 않는다. 계획과 현재 코드가 충돌할 때 영향받는 부분만 조정한다. 제품 의미가 달라지는 결정은 확인한다.

## 2. 구현 반복

1. 계획이 있으면 현재 단계를 `in-progress`로 갱신한다. 실제 의존 순서를 따라 검증 가능한 단위부터 구현한다.
2. 기존 패턴과 필요한 전문 스킬을 사용한다. 특정 계층 구조를 도입하거나 리팩터링 범위를 넓히지 않는다.
3. 동작 변경에는 정상 경로, 주요 실패와 경계 조건을 검증하는 의미 있는 테스트를 추가·갱신한다. 버그는 가능하면 수정 전 실패하는 재현 테스트를 만든다. 문구·문서·단순 스타일 변경에 구현을 그대로 복제한 테스트를 만들지 않는다.
4. [검증 절차](references/verification.md)에 따라 필요한 포맷·정적 분석·테스트·빌드를 실행한다. 관련 없는 전체 검사를 반복하지 않는다.
5. 실제 완료 증거를 기록한 뒤에만 단계를 `done`으로 표시한다. 필수 수동 확인이 남아 있으면 미완료 항목으로 유지한다. 자동 테스트 통과와 사용자 확인은 별개다.
6. 승인된 다음 단계가 남으면 계속한다. 자동 커밋, 컨텍스트 초기화, 단계별 승인 대기를 기본 절차로 넣지 않는다.

## 3. 변경 범위와 리뷰

브랜치 전체 변경을 검토하려면 확인된 기준 브랜치와의 merge-base부터 현재 코드까지 본다. staged·unstaged·untracked도 포함한다. 기준을 확인할 수 없으면 비교 범위를 명시하고 임의로 `main`을 가정하지 않는다.

- 요청과 관계없는 자신이 만든 변경만 제거한다. 사용자 변경이나 기존 코드는 정리 대상으로 삼지 않는다.
- 동작 정확성, 경계·의존 방향, 테스트의 의미, 불필요한 복잡성, 디버그 잔여물, 필요한 생성 파일을 확인한다.
- 실제 제공되는 리뷰 스킬이 있으면 활용한다. 없으면 같은 관점을 직접 검토한다. 단일 에이전트의 검토를 독립 리뷰라고 표현하지 않는다.
- 범위 안의 결함은 수정 후 영향을 받는 검증을 다시 실행한다. 관련 없는 문제는 별도 관찰로 보고한다.
- 작성한 계획·리뷰·인계 문서를 일괄 삭제하지 않는다.

## 4. 완료와 인계

결과, 변경한 주요 파일, 실행한 검증과 한계, 미해결 사항을 전달한다. 긴 작업은 기존 계획에 상태와 다음 행동을 남긴다. 커밋·푸시·PR 생성까지 요청된 경우에만 이어서 수행하고, 이미 받은 권한은 다시 묻지 않는다.
