# 장애 회고

누구의 잘못인지보다 어떤 조건과 절차가 문제를 가능하게 했는지 설명한다.

1. 증상, 영향, 환경, 시작·탐지·복구 시각, 적용한 조치, 관련 로그·커밋·PR을 대화에서 추출한다. 빠진 핵심 정보만 묻고 자료가 불완전해도 확인되지 않은 부분을 표시하며 진행한다.
2. 관련 코드와 Git 기록을 좁게 확인한다. 연결된 도구로 해당 CI·배포 기록을 읽을 수 있으면 함께 확인한다. 광범위한 계정 자료를 수집하지 않는다.
3. [양식](references/debrief-template.md)에 사실, 추정, 알 수 없는 내용을 구분한다. 시간에는 시간대를 붙이고 근거 없는 정확한 시각이나 영향 수치를 만들지 않는다.
4. 직접 원인과 기여 요인을 분리한다. 결론을 로그·코드·변경 이력과 연결한다. 시간상 앞선 변경이라는 이유만으로 원인이라고 단정하지 않는다.
5. 후속 조치를 예방·탐지·대응으로 구분한다. 각각 구체적 행동, 확인 방법, 담당·기한을 기록한다. 미정인 담당자와 기한은 미정으로 남긴다.
6. 기본적으로 `docs/workflow/<주제>/debrief.md`에 저장한다. 기존 회고가 있으면 요청에 맞게 갱신하거나 별도 사건으로 구분한다.

회고 요청만으로 코드를 고치거나 이슈·댓글·메시지를 게시하지 않는다. 이슈 초안을 요청받으면 저장소 양식에 맞춰 복사 가능한 초안을 만든다. 결과에는 영향, 근거 있는 원인, 중요한 후속 조치와 남은 불확실성을 요약한다.
