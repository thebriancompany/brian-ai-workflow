# 브랜치 리베이스

로컬 이력 갱신과 원격 이력 재작성을 구분한다. 리베이스 요청 자체에 원격 강제 push가 포함되지는 않는다.

## 준비

1. 현재 브랜치, 원격, 작업 트리, 진행 중인 merge/rebase/cherry-pick을 확인한다. 기존 작업이 진행 중이면 임의로 중단하거나 새 리베이스를 시작하지 않는다. detached HEAD나 기준 브랜치 자체이면 대상부터 확인한다.
2. 사용자가 지정한 기준을 우선하고, 없으면 현재 PR 대상이나 원격 기본 브랜치에서 확인한다. 여러 후보가 있으면 묻는다. 없는 기준을 추측하지 않는다.
3. 변경이 남아 있으면 사용자 지시와 이미 받은 권한을 확인한다. 보관 권한이 없으면 구체적인 변경 목록을 제시하고 보관 후 진행 여부를 확인한다. 임의 커밋·삭제는 하지 않는다.
4. 보관할 경우 untracked 포함 여부를 확인해 필요한 변경만 stash하고 생성된 stash의 OID를 기록한다. 비밀 파일이나 ignored 파일까지 일괄 포함하지 않는다. 기존 stash를 자신의 것으로 착각하지 않는다.
5. 원래 HEAD를 기록하고 고유한 로컬 백업 브랜치를 만든다. 대상 원격과 기준 브랜치를 fetch한 뒤 정확한 기준 커밋을 확인한다. fetch 실패 시 최신 상태라고 말하지 않는다.

## 실행과 충돌

- 이미 기준을 포함하면 리베이스를 생략하고 보관했던 변경을 복원한다.
- merge 커밋이 있으면 프로젝트의 이력 보존 방식을 확인한다. 임의로 중요한 merge 구조를 평탄화하지 않는다.
- 확인한 기준에 리베이스한다. 충돌은 양쪽 의도와 관련 테스트를 읽고 명확한 범위에서 해결한다. 전체 파일을 한쪽 버전으로 덮어쓰지 않는다.
- 제품 결정이 필요하거나 안전하게 해결할 근거가 없으면 이 작업에서 시작한 리베이스만 중단해 원래 상태로 돌아간 뒤, 충돌과 필요한 결정을 설명한다. 진행 중인 상태를 남겨 달라는 사용자의 요청이 있으면 따른다.

## 복원과 확인

보관한 변경은 성공·실패·변경 없음 등 모든 종료 경로에서 기록된 OID로 `stash apply`한다. 먼저 적용 결과를 확인하며 `pop`으로 바로 제거하지 않는다. 복원 충돌이 나면 stash와 백업을 보존하고 파일을 나열한다. 자동 reset·clean을 실행하지 않는다.

복원이 확인되고 보관본 제거가 허용된 경우에만 OID와 일치하는 stash 항목을 찾아 제거한다. 다른 stash의 순서 번호를 추측하지 않는다.

원래 커밋 범위와 새 범위를 비교하고 충돌 해결의 영향을 받는 테스트를 실행한다. 최종 브랜치·HEAD, 복원 여부, 검증, 백업 위치를 보고한다. 원격 이력 재작성까지 명시적으로 승인된 경우에만 원격 HEAD를 확인해 예상 OID를 고정한 `--force-with-lease`를 사용한다. 일반 `--force`는 사용하지 않는다.
