# 긴급 수정

계획 문서 작성보다 증상, 원인, 수정과 증거에 집중한다.

1. 증상, 발생 조건, 영향받는 환경, 기대 동작을 정리한다. 오류 메시지와 로그가 있으면 민감 정보를 제거하고 근거로 사용한다.
2. 적용되는 `AGENTS.md`와 관련 코드·호출부·최근 변경·테스트를 좁게 확인한다. 근본 원인과 추정을 구분한다.
3. 기존 변경을 보존하고 적합한 작업 브랜치를 사용한다. 브랜치 이름은 프로젝트 규칙을 따른다. 없으면 `feature/hotfix-<주제>`를 쓴다.
4. 가능한 경우 수정 전 실패하는 회귀 테스트나 최소 재현을 만든다. 기존 테스트 도구가 없으면 재현 절차와 실행 결과를 남긴다. 설치 불가능한 환경을 통과로 처리하지 않는다.
5. 원인을 해결하는 최소 변경을 적용한다. 새로운 기능, 관련 없는 정리, 불필요한 TODO를 끼워 넣지 않는다. 공유 코드를 고치면 관련 호출자 영향을 확인한다.
6. 저장소에서 확인한 포맷·정적 분석·회귀 테스트와 필요한 인접 테스트를 실행한다. 동작을 증명하는 검증을 선택하고 테스트 기대값을 무작정 완화하지 않는다.
7. diff를 다시 읽고 원인 해결 여부, 부작용, 오류 경로, 테스트의 의미를 검토한다. 수정 후 영향을 받는 검사만 다시 실행한다.

같은 실패가 진전 없이 반복되면 기본 3회 이내에 원인·시도·차단 요소를 정리하고 필요한 정보를 묻는다. 데이터 마이그레이션, 공개 계약 변경, 광범위한 구조 변경이 필요하면 이를 알리고 짧은 계획으로 범위를 재설정한다. 파일 개수만으로 긴급 수정 가능 여부를 결정하지 않는다.

완료 시 원인, 변경, 검증, 잔여 위험과 필요한 복구 방법을 알려준다. 부분 완화라면 완전 해결과 구분한다. 사용자 요청에 커밋·푸시·PR·배포가 포함되어 있는 경우에만 해당 작업을 이어서 수행한다.
