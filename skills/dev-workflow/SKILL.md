# 개발 워크플로우

요청을 검증된 결과로 연결한다. 언어, 프레임워크, 아키텍처를 미리 정하지 않는다.

## 시작과 단계 선택

1. 현재 요청과 이전 결정을 읽고 이번 작업의 끝을 정한다. 구현, 문서 작성, 리뷰, PR 중 사용자가 요청한 범위를 따른다.
2. 적용되는 `AGENTS.md`, 관련 코드, 의존성 및 잠금 파일, 실행 스크립트와 CI를 읽는다. 확인된 규칙과 추정한 관례를 구분한다.
3. 관련 계획이나 진행 기록이 있으면 코드와 대조하여 재사용한다. 최근 날짜라는 이유만으로 다른 주제의 문서를 선택하지 않는다.
4. 아래에서 필요한 단계만 선택한다. 이미 명확한 요구사항에 브레인스토밍을 강제하지 않는다.

| 현재 상황 | 진행 방식 |
| --- | --- |
| 목표나 해결 방법이 불명확함 | 아이디어 정리 → 계획 → 구현 → 리뷰 |
| 요구사항이 명확한 기능 | 계획 → 구현 → 리뷰 |
| 작고 명확한 수정 | 구현 → 관련 검증 → 변경분 리뷰 |
| 장애나 긴급 회귀 버그 | 재현 → 최소 수정 → 회귀 검증 → 리뷰 |
| 기존 계획을 이어서 구현 | 현재 코드와 완료 증거 확인 → 미완료 단계 재개 |
| 계획·리뷰·회고만 요청 | 해당 산출물에서 종료 |

## 단계별 스킬

사용 가능한 스킬 목록에서 필요한 스킬만 읽는다. 같은 묶음이 설치되어 있으면 아래 상대 경로로도 읽을 수 있다. 도구 이름을 추측해 호출하지 않는다.

- [dev-brainstorm](../dev-brainstorm/SKILL.md): 문제, 대안, 결정 정리.
- [dev-plan](../dev-plan/SKILL.md): 파일과 검증 방법이 명확한 실행 계획.
- [dev-build](../dev-build/SKILL.md): 구현, 테스트, 검증, 진행 기록.
- [dev-review](../dev-review/SKILL.md): 근거가 있는 발견 사항을 통합한 리뷰.
- [dev-hotfix](../dev-hotfix/SKILL.md): 긴급 버그 수정.
- [dev-create](../dev-create/SKILL.md): 새 프로젝트의 최소 구성 생성.
- [dev-pr](../dev-pr/SKILL.md): 요청된 커밋, 푸시, PR 생성.
- [dev-rebase](../dev-rebase/SKILL.md): 현재 브랜치를 기준 브랜치 위로 갱신.
- [dev-refine](../dev-refine/SKILL.md): 기존 접근 방식 다듬기.
- [dev-plan-review](../dev-plan-review/SKILL.md): 기존 계획의 구현 가능성 검토.
- [dev-debrief](../dev-debrief/SKILL.md): 장애 회고.
- [dev-writing](../dev-writing/SKILL.md): 기술 문서의 한국어 표현 개선.

단계 스킬을 찾지 못하면 해당 단계의 입력·결정·결과·검증을 직접 수행한다. 설치 누락은 알리되, 존재하지 않는 도구나 스킬을 실행했다고 말하지 않는다.

## 흐름을 유지하는 규칙

- 사용자가 전체 구현을 요청했으면 승인된 범위 안에서 다음 단계로 계속 진행한다. 단계마다 재승인, 새 채팅, 컨텍스트 초기화를 요구하지 않는다.
- 답이 없으면 제품 의미나 데이터 계약이 바뀌는 문제만 질문한다. 되돌릴 수 있는 구현 선택은 근거와 가정을 기록하고 진행한다.
- 필요한 전문 스킬이 실제로 제공될 때만 사용한다. 동반 플러그인, 특정 MCP, 서브에이전트가 없어도 단일 에이전트로 완수한다. 병렬 위임은 사용자나 적용 지침에서 허용한 경우에만 한다.
- 기존 구조와 명령을 우선한다. 모든 프로젝트에 계층 구조, 상태 관리 도구, 테스트 파일 수를 일률적으로 강제하지 않는다.
- 검증은 실제 실행 결과로 기록한다. 미실행·실패·수동 확인 대기를 통과로 바꾸지 않는다.
- 구현 요청만으로 커밋·푸시·PR·배포를 추가하지 않는다. 사용자가 이미 요청한 동작은 반복 확인하지 않는다. PR 생성 권한에 병합·배포 권한은 포함되지 않는다.

## 산출물과 재개

프로젝트의 기존 문서 경로를 우선한다. 없으면 `docs/workflow/<주제>/` 아래에 필요한 `brainstorm.md`, `plan.md`, `review.md`, `handoff.md`만 만든다. 작은 수정에 문서 묶음을 강제하지 않는다. 날짜가 필요하면 사용자의 시간대를 따른다.

긴 작업이나 중단·재개 시 [인계 양식](references/handoff.md)을 사용한다. 진행 상태를 기록하는 것은 커밋·배포 완료를 뜻하지 않는다. 최종 답변에는 결과, 검증, 미해결 사항, 관련 파일을 간단히 제시한다.
