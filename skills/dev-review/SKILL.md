# 코드 리뷰

근거가 있고 행동으로 옮길 수 있는 문제를 찾는다. 발견 사항 수를 채우기 위한 취향 지적은 하지 않는다.

## 범위 설정

1. 사용자가 지정한 파일·디렉터리·PR·기준 브랜치를 우선한다. 공백이 포함된 경로를 공백으로 쪼개지 않는다.
2. 기본 브랜치는 기존 PR의 대상, 프로젝트 설정, 원격 기본 브랜치 순서로 확인한다. 현재 브랜치의 upstream이 곧 PR 대상은 아니다. 서로 충돌하거나 불명확하면 확인한다.
3. 전체 브랜치 검토는 확인한 merge-base부터 현재 변경까지 읽고 staged·unstaged·untracked를 포함한다. 커밋된 PR만 요청받았으면 해당 diff에 한정한다.
4. 기준 브랜치에서 로컬 변경만 있으면 그 변경을 검토한다. 변경도 없고 대상도 없으면 범위를 묻는다. 전체 저장소 감사로 임의 확대하지 않는다.
5. `AGENTS.md`, 주변 코드와 호출부, 관련 테스트를 읽어 실제 동작을 확인한다. diff 리뷰에서는 이번 변경이 유발한 문제를 우선하고 기존 문제는 구분한다.

## 검토와 보고

[리뷰 관점](references/review-lenses.md)에서 관련 있는 관점만 적용한다. 단일 에이전트로 수행할 수 있다. 서브에이전트를 이용하는 경우에도 현재 환경의 위임 권한을 먼저 따른다. 관점별 검토가 독립 에이전트 리뷰였다고 꾸미지 않는다.

발견 사항에는 재현 조건, 영향, 코드 위치, 수정 방향을 담는다. 단순한 가능성이나 확인하지 못한 의심은 사실로 보고하지 않는다. 수행하지 않은 테스트를 통과했다고 쓰지 않는다.

[결과 형식](references/review-report.md)에 따라 중복을 합치고 `FINDING-01` 형태의 ID를 부여한다. 기본 저장 위치는 `docs/workflow/<주제>/reviews/<실행식별자>.md`다. 기존 보고서를 덮어쓰지 않고 보존하며, 문서 생성을 원하지 않으면 채팅으로만 전달한다.

발견 사항이 없으면 검토 범위에서 확인된 문제가 없다고 설명하고 남은 검증 한계를 함께 적는다. 리뷰가 불완전하면 전체 통과 판정을 내리지 않는다.

## 후속 행동

리뷰만 요청받았으면 제품 코드를 수정하거나 PR에 댓글을 게시하지 않는다. 수정까지 요청받았으면 지정된 발견 사항을 고치고 영향을 받는 검증을 실행한다. PR 댓글 게시 요청이 있을 때만 게시하며, 기존 댓글을 확인해 중복을 피한다.
