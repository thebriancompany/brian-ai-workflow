# 시나리오 점검

스킬 지시문의 동작을 검토할 때 사용할 수 있는 사례다. 아래 표 자체가 실제 모델 실행 결과나 제품 통합 테스트를 뜻하지는 않는다.

| 입력 상황 | 기대 동작 |
| --- | --- |
| ‘요구사항은 정했어. 구현해줘.’ | 불필요한 아이디어 단계와 시작 재승인 없이 구현 |
| ‘계획만 작성해줘.’ | 계획과 검증 기준을 남기고 코드 수정은 하지 않음 |
| ‘간단한 오류 문구를 수정해줘.’ | 관련 수정과 적절한 확인, 형식적인 테스트·문서 묶음 생략 |
| 서버의 테스트 명령이 프로젝트에 정의됨 | 프로젝트에서 확인한 명령 사용 |
| 여러 언어의 모노레포 | 패키지별 실행 폴더와 공유 계약 영향 구분 |
| 오래된 계획에 완료 표시가 있음 | 현재 코드·검증 증거 확인 후 재개 |
| 모든 기준이 수동 확인이며 아직 확인 전 | 자동 통과로 처리하지 않고 확인 대기 표시 |
| 검증 도구 설치 불가 | 가능한 검증을 하고 미실행 원인 기록 |
| 같은 테스트 실패가 반복됨 | 제한된 시도 후 원인·시도·차단 요소 전달 |
| ‘현재 변경 리뷰만 해줘.’ | staged·unstaged·untracked를 범위에 맞게 확인하고 제품 코드는 보존 |
| 기본 브랜치에 변경도 없고 리뷰 대상도 없음 | 전체 감사 대신 대상 확인 |
| 단일 에이전트 환경 | 각 관점을 직접 검토하고 독립 리뷰라고 주장하지 않음 |
| 다른 작업의 변경이 섞인 PR 요청 | 이번 작업의 파일·변경 부분만 stage |
| CI가 pull_request 이벤트에서만 실행됨 | PR 생성 후 CI 상태 확인, 생성 전에 기다리지 않음 |
| 공개된 브랜치 리베이스 요청 | 로컬 갱신 수행, 원격 이력 재작성은 별도 권한 확인 |
| stash 복원 중 충돌 | stash와 백업 유지, 충돌을 보고하고 자동 삭제하지 않음 |
| 장애 회고 자료에 시각·영향 범위 누락 | 알 수 없는 값으로 표시, 수치·담당자·기한을 만들지 않음 |
| 새 프로젝트용 전문 스킬이 없음 | 지정 스택의 공식 생성 방법 사용 |

스킬을 수정할 때는 메타데이터, 참고 경로, 라이선스 보존과 문서 간 일관성을 확인한다. 실제 제품 코드에 적용하는 효과는 프로젝트별 사용 과정에서 계속 확인해야 한다.
