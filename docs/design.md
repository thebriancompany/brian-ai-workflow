# 설계 원칙

## 유지한 흐름

아이디어 정리, 계획, 구현, 리뷰를 중심으로 접근 개선, 계획 기술 검토, 프로젝트 생성, 긴급 수정, PR, 리베이스, 장애 회고와 글쓰기 지침을 제공한다. 단계 간에는 문서와 검증 증거를 전달한다.

전체 흐름을 선택하고 이어가는 `dev-workflow`를 추가했다. 나머지 스킬은 특정 단계만 요청할 때도 사용할 수 있다. 기술별 분석 역할은 계획·리뷰 스킬 안의 관점으로 통합해, 별도 에이전트 설정 파일 없이도 수행할 수 있도록 했다.

## 범용 개발에 맞춘 변경

| 항목 | 적용 방식 |
| --- | --- |
| 언어·프레임워크 규칙 | 저장소 설정, 코드, 공식 버전 문서에서 확인 |
| 아키텍처 | 프로젝트가 선택한 구조와 의존 방향 사용 |
| 테스트 | 요구사항과 위험에 맞는 검증, 문서·문구 수정은 적절한 구조 검사 |
| 큰 계획 | 동작·검증 가능한 단계로 분해하고 상태와 증거 기록 |
| 작은 변경 | 불필요한 문서와 계획 단계를 생략 |
| 프로젝트 생성 | 전문 스킬이 없으면 공식 생성 도구와 문서 활용 |
| 리뷰 | 동작, 구조, 테스트, 단순성, 제출 준비 관점 |
| 기술 글쓰기 | 영어 문법 규칙 대신 한국어 기술 문서의 정확성과 전달력 |

## Codex에 맞춘 변경

- 호출은 `$dev-plan` 같은 스킬 이름을 사용한다.
- 스킬마다 표준 `name`, `description`과 한국어 본문을 두고 `agents/openai.yaml`에 한국어 UI 정보를 둔다.
- 특정 제품의 도구명, 인자 치환 변수, 강제 모델 선택, 실행 권한 선언에 의존하지 않는다.
- `AGENTS.md`와 제공된 스킬·도구를 사용하며 없는 도구를 추측하지 않는다.
- 질문은 답이 필요한 결정에 한정하고 질문 도구가 없는 환경에서는 대화로 진행한다.
- 병렬 에이전트는 필수가 아니다. 각 환경에서 허용된 경우에만 위임한다.
- 단계마다 강제로 멈추거나 새 채팅을 만들지 않는다.
- 개인 취향을 저장소 규칙에 자동 기록하지 않는다.

## 신뢰할 수 있는 완료 처리

검증 명령의 성공과 요구사항의 충족을 연결한다. 계획에 적힌 명령도 실제로 유효하고 필요한지 검토한다. 명령을 맹목적으로 실행하는 자동 실행기는 포함하지 않는다.

실패를 숨기거나 무한 재시도하지 않는다. 실패가 반복되면 원인과 시도한 내용을 기록하고, 진행 가능한 나머지 작업과 차단된 작업을 구분한다. 리뷰와 인계 자료를 자동 삭제하지 않는다.

기존 사용자 변경을 보존한다. 작업 관련 변경만 커밋하고 요청된 범위에서만 원격에 게시한다. 리베이스에서는 원래 HEAD, 백업, 직접 생성한 stash를 식별해 복원한다.

## 배포 구조

13개 스킬을 함께 배포한다. 세부 단계 스킬의 참고 자료는 각 폴더 안에 둔다. 전체 흐름 스킬만 다른 단계 스킬을 참조하며, 스킬이 없을 때의 직접 수행 경로도 제공한다.

스킬 폴더를 Codex의 개인 또는 프로젝트 스킬 경로에 복사해 사용한다. 별도 설치·검사 프로그램이나 실행 환경은 포함하지 않는다. 심볼릭 링크로 연결한 경우에도 스킬 문서를 직접 읽으므로 추가 프로그램이 필요하지 않다.
